# Agent and native reverse-engineering stack comparison

**Prepared:** 2026-10-11  
**Scope:** the relevant entries in the current 384-record `resources.json`, plus the external IDA bridge that REA’s current IDA adapter documentation names as a prerequisite. This is a role comparison—not an installation guide or compatibility certification.

## The short version

These are **not four equivalent agent-workflow repositories**:

- **[REA](https://github.com/morluto/rea)** is a cross-target **agent workflow/orchestration layer**, especially for evidence-backed reverse-engineering investigations. It is not the only agent-oriented workflow in the full catalog: [Universal Modder](https://github.com/rehan-remade/universal-modder) is a separate, game-modding-focused workflow (see §6). REA offers one MCP/CLI surface across multiple target types; for native binaries, it still needs an analysis engine/provider.
- **[IDA Pro](https://hex-rays.com/ida-pro), [Binary Ninja](https://binary.ninja/), [Hopper](https://www.hopperapp.com/), and [Ghidra](https://github.com/NationalSecurityAgency/ghidra)** are **analysis platforms/engines**. They load binaries and provide disassembly, decompilation or pseudocode, navigation, and other analysis features. They are not general application-workflow orchestrators.
- **MCP servers** are the bridges that expose an engine to an agent. Some are separate repos; some are built into the product. The product and its bridge must not be conflated.
- For an agent using REA on native code, the basic shape is **agent → REA → one supported native provider**. For direct, product-native agent access it is **agent → that product’s MCP server**. Running multiple MCP bridges against one analysis database is usually unnecessary and can create duplicate tools or state ambiguity.
- Analysis platforms do **not** replace Android DEX tools, engine-specific game-asset readers, runtime instrumentation, network-capture tools, or mod mergers. The task matrix below lists those additions.

### Important IDA/REA compatibility note

As checked against the current upstream documentation on **2026-10-11**, REA’s IDA-provider guide describes an adapter for **mrexodia/ida-pro-mcp**. The official [Hex-Rays `ida-mcp`](https://github.com/HexRaysSA/ida-mcp) exposes a different tool surface. REA issue [#1416](https://github.com/morluto/rea/issues/1416) is still open and documents that the two surfaces do not currently overlap. Therefore:

- **Want REA’s evidence-backed workflows with IDA?** Follow the exact provider profile/version in REA’s current IDA guide; this currently means the mrexodia-compatible server path, with its extra setup and the upstream’s recommendation to prefer the official server noted.
- **Want an agent to operate IDA directly?** Use the official Hex-Rays IDA MCP with a supported IDA install; REA is not required for that direct path.
- **Do not configure both just because both are called IDA MCP.** They are separate servers with different APIs. Running both can duplicate tools and contradict the official server’s advice to disable other IDA MCP servers.

## 2. What REA itself covers, and what it requires

This is the broadest overview of the workflow repository specifically. Requirements below are **per target**: installing REA does not automatically install or license each external engine.

| Task / target | REA’s documented coverage | Additional software or catalog repository needed | Main boundary |
|---|---|---|---|

| **Recorded Linux crashes** | Reads recorded notes, thread registers/signals, and optional mapping candidates. | Caller-supplied `pwntools` on Linux x64; optional [GDB](https://sourceware.org/gdb/) / pwndbg. pwndbg is not cataloged as a separate repo. | It analyzes a recorded crash artifact; this is distinct from attaching to and debugging a live process. |

| **JEB analysis project** | Can read engine-backed project units, artifact digests, and type/method pseudocode. | A running JEB client exposing MCP, configured through `REA_JEB_MCP_URL`; JEB is not a separate repo record in the current catalog. | It depends on the caller’s JEB installation/license and matching integration; not a built-in decompiler shipped with REA. |
| **Firmware** | Firmware region/extraction results and handoffs to native analysis. | [Binwalk](https://github.com/ReFirmLabs/binwalk) or Unblob on Linux; Unblob is not a separate current catalog record. | **Apple bundles / package resources** | Inventories, digests, plist and Apple-bundle anatomy, and supported extracted resources; selected native metadata workflows. | macOS/Xcode system utilities for some facets; [Hopper](https://www.hopperapp.com/) or Ghidra for native code. | Support is facet-specific. Extraction does not recreate all app source or unknown proprietary resources. |
| **Process behavior** | On Linux/macOS with a native PTY, records terminal output, interactions, exit/filesystem observations, and compares runs. | Linux/macOS process environment. Use [GDB](https://sourceware.org/gdb/), [LLDB](https://lldb.llvm.org/), [WinDbg](https://learn.microsoft.com/en-us/windows-hardware/drivers/debugger/), [x64dbg](https://github.com/x64dbg/x64dbg), or Frida when instruction-level/live-process control is needed. | Process capture is not the same as an interactive debugger or general in-process instrumentation. |

**REA’s minimum general prerequisites:** Node.js/npm and an MCP-capable agent (for agent use). Native code additionally needs one supported engine/provider. The current REA README lists Node.js 22.19+, 24.11+, or 26+; release-package capabilities may lag the source repository, so verify the actual installed release and live MCP tool list.

| Priority | Practical choice | Why | Add/avoid |
|---|---|---|---|

## 5. Other relevant cataloged analysis repos: what they add

### Answer to “is REA the only real agent workflow?”

**No, not across the full catalog.** The more precise claim is: **REA is the dedicated cross-target, evidence-oriented reverse-engineering workflow** in the analysis-tool set. **Universal Modder is another real agent workflow** and is more directly aimed at end-to-end PC game modding. **AI Game Modding Guides** and **Replica Skill** provide agent workflows at the instruction/skill layer, while **UnityRuntimeExplorer** and the MCP servers expose specialized tools to agents rather than orchestrating the entire job.

For **Steam game modding/recon/build/test**, start with Universal Modder’s engine route and bring in the matching asset/code/runtime tools. For **Android apps, general native binaries, websites, .NET, or cross-target evidence-led reverse engineering**, REA is the stronger workflow layer, with its required provider or target tools added. Neither workflow makes the other redundant.

## 7. Catalog boundaries and no-substitute notes

- The relevant 384-record catalog includes **REA, Ghidra, Ghidra MCP, official Hex-Rays IDA MCP, IDA Pro/Free, Binary Ninja, Binary Ninja MCP docs, Binary Ninja Headless MCP, Binary Ninja Cloud, Hopper, Cutter, Rizin, radare2, radare2-mcp, Frida, and Objection**.
- **mrexodia/ida-pro-mcp** is named in REA’s current provider documentation but is **not a separate record** in `resources.json`; it is treated here only as an external dependency note, not added to the catalog.
- No native RE platform recovers proprietary original source, original game project files, private server state, or every asset format from executable code alone.
- Static platforms (IDA, Binary Ninja, Hopper, Ghidra, Rizin/Cutter) are not loaders/managers. Dynamic tools (Frida, debugger) are not static decompilers. Engine asset readers do not necessarily inspect code. Mod managers do not necessarily merge content semantics.
- For the full Steam engine-family coverage and Rust project comparisons, see the previously prepared **`repo-completeness-review.md`**. This file adds the deeper agent/native tool-stack comparison; neither file modifies the curated catalog or map.
